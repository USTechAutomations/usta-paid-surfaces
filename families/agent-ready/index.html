What one row saysthe lane's own words

one row on the public agent-ready table: what this shop's own robots file says about named shopping assistants, and how far a reader gets up the ladder on its public product pages

The second half of that is a ladder, and it is fixed and ordered on purpose. A row saying “stops at step three” means nothing unless step three is the same step it was last month:

  1. Your robots file lets the assistants we test for read a product page
  2. A product page actually comes back, as a page and not as a block
  3. The page says, in a way a machine reads, that this is a product
  4. The price is there in a way a machine reads, and only one price is
  5. Whether it is in stock is there in a way a machine reads
  6. The product carries a code an assistant can match against other shops
  7. There is a basket an assistant can find without guessing
  8. The checkout page can be reached
  9. The payment page can be reached

What this measures, said plainly: what an assistant that reads pages can do. It does not run your scripts and it does not sign in. A shop whose basket only exists after a browser runs its code genuinely does stop a reader, and that is what the row says — not that the shop is broken.

This is a record of what our reader saw on pages your shop publishes to everybody. It is not a security test, not an audit, and not advice.

The wall this never climbs over6 things it will not do

The rungs a robot shopper has to climb, and the wall it is never allowed to climb over.

The table's whole claim is "an AI shopping assistant can / cannot buy here, and here is the rung it falls off". So the rungs have to be a fixed, ordered, named list. If the list could change between two runs, "breaks at step 3" would mean two different things on two different days and the dated history - the only moat this product has - would be worthless.

THE WALL. The ladder stops at "the payment page is reachable". Reaching a payment page is a fact about somebody's shop. Filling one in is buying something from a stranger with their own money, in their own name, with no human awake. There is no version of this product that needs it, so the steps that would do it are not steps at all - they are named here only so that asking for one is a refusal with a reason instead of a KeyError.

The wall is enforced three ways, because a rule that lives only in a docstring is a wish: 1. `climb()` refuses any name outside RUNGS. 2. Nothing in this whole package can send anything to anybody - no POST, no socket, no urlopen. Whatever fetches pages is handed in from outside. A drill greps for it. 3. The refusal is printed on the face of every page we hand a customer.

What decides the order rows come inread out of the lane, not restated

The page the whole table is published as, and the two guards that stand in front of it.

WHAT ORDER THE SHOPS COME IN IS THE PRODUCT. A table where paying moves you up is an advert wearing a table's clothes, and every shop on it and every reader of it has been misled. So the ordering is not written here: it is handed to the shared sorter, which is given a view built from three named fields - the id, the name and the day the shop was added - and REFUSES OUTRIGHT, by raising, if a payment field ever reaches it. A guard that quietly dropped the bad field would teach nobody it had fired, and the next person to read the code would widen the list because nothing seemed to happen.

The tie-break inside the shared sorter reads a field called `provider_id`, which is the other table's name for its id and is simply absent here. So the rows are put in id order BEFORE they are handed over, and Python's sort keeps equal keys in the order it was given them - two shops with the same name added on the same day come out in id order rather than in whatever order the database felt like. The alternative is a one-line change in shared code, and that change is written out in this lane's migration note rather than made here.

AND THE WORDING GUARD READS THE FINISHED PAGE. This is a table with named businesses' names on it that their competitors read. It may never rank them - not "the best", not "better than", not "our top pick". The page's own promise not to rank is exempt from the guard, ONCE PER LINE: those sentences contain the exact phrases the guard hunts for, so dropping them is right, and dropping every copy of them is not. A ranking line written as a character-for-character copy of a promise bullet leaves a second copy behind in the checked text, and that copy stops the page.

A page the guard stops is not simply not published. It writes a DATED row saying the table is held today and why - see `run.publish_table()`. Stopping the render would leave yesterday's page standing as the newest thing we published, which is publishing it again with none of today's checks passing.

The rule itself: alphabetical by shop name, then the day the shop was added, then the shop id. Nothing about money is in the view the sorter is handed, and handing it one raises rather than being ignored.

The only things the sorter is shown are “shop_id”, “name”, “added_on”. Handing it anything about money raises rather than being quietly dropped, because a guard that fires silently teaches nobody it fired.

What we may never claimchecked on this build

The list of assistant names this table asks each robots file about is unverified, and it is expected to stay that way. Nobody publishes a register of shopping assistants, and the companies behind them rename and retire these strings without telling anybody.

So the lane’s own switch says no, always, in these words: “the rule this product is built on has not been checked against the published text yet, so no missing-information finding can be sold”

Counted out of the rules file as this page was built: 10 assistant names listed, 0 of them verified. What the table reports instead is checkable to the character: for each named string, what that shop’s own robots file says about it, against a copy of the file we keep.

Why nobody is on this table2 gates, one of them shut

A public table with real companies’ names on it needs two separate written permissions, and only one of them exists.

  • May a machine of ours read other companies’ public websites at all? ACTIVE.The operator wrote that decision down and dated it, and it was approved on 2026-08-25. It is re-read before every fetch rather than remembered, and changing one word in it stops every new read with no change to any code.
  • Which shops belong on the table, and where did that list of names come from? UNKNOWN.projects/agent_ready/rules/shop-list-source.json reads `terms_status: NOT_READ`. Nobody has read the terms of the source these names would come from, and no page is even named yet

So the shut gate is where the list of names comes from, and this is what the lane’s own nightly report says about it, word for word:

“nothing is wired to fetch with, so no shop was read tonight. The operator decision about reading other people's shops is ACTIVE, but that is not the gate that is shut: nobody has written down which shops belong on this table. projects/agent_ready/rules/shop-list-source.json reads `terms_status: NOT_READ`. Nobody has read the terms of the source these names would come from, and no page is even named yet”

The declaration that says so is a dated file the lane reads and may never write. In its own words:

  • Where the names come fromNOTHING IS NAMED. This is the honest state and it is worse than an unread terms page: no source has been proposed at all. The spec names none, the wave plan names none, and no file on this disk names one.
  • Why this is not clearedThere are only two ways a list of shops can exist, and neither has happened. EITHER it is taken from somebody else's list of shops - a top-sites list, a platform's public directory, a crawl dataset - in which case that list has a licence somebody has to read first, and no such list has even been proposed. OR the shops are chosen by us one at a time, which is a business decision about naming real companies on a public page, and the operator's approval of 2026-08-25 does not make it: it permits reading sites, not choosing whose names go on a table.
  • What this lane must never doFill this file in from its own general knowledge of well-known shops. A list of names a machine chose for itself is the self-granting defect this whole estate is built against, and here it would put real named businesses on a public page with no source behind the choice. The spec's own scar says it: a page that makes a claim about a named business it cannot stand behind is a lawsuit rather than a product.
  • What would change thisEither (a) somebody names a list source, reads its licence, and writes the four clearance fields below plus the shops into this file; or (b) the operator writes down which shops go on the table and why, and this file records that as the source with the operator named in terms_read_by. Until all four clearance fields are here and terms_status reads CLEARED, run.FETCHER stays None, nothing is read, and no row exists.

And the approval does not cover it. approvals/read_public_sites.md, status ACTIVE, approved_on 2026-08-25, permits READING a company's public pages once its robots file and a filed permission note allow it. It says nothing about which companies belong on a public comparison table, and it explicitly refuses self-granting: 'a machine may write a permission NOTE from evidence, never a permission DECISION.'

That declaration was written on 2026-08-25 and it reads NOT_READ. It is a file the lane reads before it reads anybody, and one it may never write: a machine that can declare its own list of names has no list of names. Where a sentence above names a file, the path is shown from inside the lane’s own folder rather than from the root of the machine that built the page.

## What we will not tell you

- that any assistant did, will or would buy from you
- how much money a rung is costing you
- that your shop is broken - a rung is a rung, not a verdict on your business
- anything about a page that is behind a sign-in
- anything we saw only once
- that another shop on this table is better than you - we do not rank shops
- that anything your shop says about itself is false

## What we never did

This is a public table, not a shopper. Everything above the payment page is us reading a page that anybody can read. Everything past it is us spending money in somebody's shop with nobody awake, and no row on any table is worth that.

- We did not type in payment details
- We did not submit a payment
- We did not create an order
- We did not complete a purchase
- We did not sign in as a customer
- We did not put a real item in a real basket

The table in it has a heading row and no rows under it. That is the honest shape of a table nobody has been cleared to be on.
